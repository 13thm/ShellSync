# ShellSync 跨网络配对方案

> 版本:v1.0(设计稿)
> 解决的问题:手机不在电脑同一局域网(用流量、在公司、在外地)时无法连接;
> 且体验必须**一键式** —— 最终用户只做两件事:装软件、扫码。不允许要求用户自购 VPS、
> 自装 frp/Tailscale、输入 IP 端口。

---

## 1. 现状与问题

### 1.1 现有配对链路(纯局域网)

```
Desktop「生成配对码」→ daemon 生成 6 位码(TTL 2min)
    → 二维码 shellsync://pair?ip=<局域网IP>&port=<port>&code=<6位>
    → 手机扫码 → 直连 http://<局域网IP>:<port> → POST /api/pair/verify 换 token
    → 之后 REST/WS 全部直连该局域网地址
```

### 1.2 为什么跨网络连不上

| 原因 | 说明 |
|------|------|
| 二维码里是私有 IP | `192.168.x.x` 只在本局域网可路由,出了网就失效 |
| 家宽无公网 IP | 国内运营商普遍 CGNAT,路由器端口转发无从谈起 |
| 无中继 | 系统里没有任何一台双方都能直达的公网节点 |

### 1.3 `deploy/` 的 frp 方案为什么不够

`deploy/` 目录的 frp 中转可用,但它是**给自己用的极客方案**:
要求使用者买 VPS、改 frps/frpc 配置、注册计划任务、手机手动输入 IP。
分发给"别人用"时,这些步骤每一步都是流失点。**它保留价值是"自托管模式"(见 §12),
不作为默认路径。**

## 2. 目标体验(用户故事)

| # | 故事 | 验收 |
|---|------|------|
| U1 | 新用户装好 Desktop,手机装好 App,扫码,完成 | **不输入任何 IP/端口**,2 分钟内配对成功 |
| U2 | 配对完成后,手机用流量打开 App | 自动连上,终端可交互 |
| U3 | 回到家里 WiFi 打开 App | 自动走局域网直连(更快),无需任何操作 |
| U4 | 用户不想用云 | 设置里有开关,关闭后回到纯局域网模式 |

## 3. 总体架构

新增第四个组件:**云中继服务 relay-server**(由软件开发者部署一台公网 VPS,全体用户共享)。

```
   手机(任意网络)                     云中继(公网 VPS)                    用户电脑
  ┌────────────┐   WSS(配对码/       ┌──────────────┐   WSS 出站长连接   ┌─────────────────┐
  │   Mobile   │   设备token)        │ relay-server │ ◄──────────────── │ daemon(开机即注册)│
  │            │ ◄─────────────────► │  信令+中继    │   多路复用数据流    │   ↓ 127.0.0.1     │
  │ REST/WS 原样│     透明字节转发      │  (不存数据)   │                   │  本机 HTTP/WS 端口 │
  └────────────┘                    └──────────────┘                   └─────────────────┘
                                                                        Desktop 照旧连 127.0.0.1
```

| 角色 | 职责 | 关键点 |
|------|------|--------|
| **relay-server**(云) | 配对码路由、会话撮合、L4 字节转发 | 只见密文,**不落盘任何业务数据**;单台即可起步 |
| **daemon** | 开机主动**出站**连云;收到会话请求时把流转发到本机 HTTP 端口 | 无需任何入站端口,CGNAT 可穿 |
| **mobile** | 配对先试局域网、失败走云端;连接层无感切换 | 应用层协议完全不变 |
| **desktop** | **零改动** | 永远连 127.0.0.1,不经过云 |

设计原则:**云中继只做"带认证的水管"**,不理解业务协议;业务鉴权(token)仍由 daemon 完成,
这样云端被攻破也不泄露数据访问能力(配合 §6 的端到端加密)。

## 4. 一键式配对流程(核心设计)

### 4.1 二维码格式 v2(向后兼容)

```
shellsync://pair?v=2
              &code=482913                                  ← 6 位配对码,TTL 2min,一次有效
              &lan=192.168.1.5:8787                        ← 局域网直连信息(可选,同网时走它)
              &cloud=relay.shellsync.example.com           ← 云中继地址
              &dev=a3f9c2...                                ← daemon 设备 ID(哈希)
```

旧版 `v=1`(只有 ip/port)继续被识别 → 老版本 App 扫新码退化为局域网模式,不报错。

### 4.2 配对时序

```
Desktop/daemon                    relay-server                       Mobile
     │  ① 开机即建立 WSS 长连接        │                                 │
     │────────────────────────────► │                                 │
     │  ② 用户点「生成配对码」          │                                 │
     │  ③ 注册 code(带TTL) ─────────► │ code→devId 入内存表               │
     │  ④ 显示二维码                    │                                 │
     │                                │                                 │
     │                                │   ⑤ 扫码,先试 lan 直连(2s 超时)    │
     │                                │   ⑥ 不通 → WSS 连 cloud           │
     │                                │      claim{code} ─────────────► │
     │                                │ ⑦ 匹配到 devId,建立 pipe          │
     │  ⑧ accept{streamId} ─────────► │◄──── 双向字节转发(隧道建立) ────── │
     │     ↕ 隧道内就是普通 HTTP         │                                 │
     │  ⑨ POST /api/pair/verify ◄─────┼─────────────────────────────────│
     │  ⑩ 返回 sessionToken ──────────┼────────────────────────────────►│
     │                                │                    ⑪ 安全存储:
     │                                │                       (cloud, devId, token)
```

注意 ⑨⑩:**配对换 token 走的就是 daemon 现有的 REST 接口,原样穿过隧道**。
这是 L4 透明隧道方案的最大红利 —— daemon 的配对/鉴权/业务代码一行不改。

### 4.3 日常连接(已配对)

```
App 启动 → 读存储 (cloud, devId, token)
  → ① 并行探测:局域网发现(快路径,~300ms) 与 云隧道握手
  → ② 谁先通走谁;局域网通了优先局域网(延迟低、不耗云端带宽)
  → ③ 断线自动切换(在家 WiFi 断开 → 无感切到云)
```

## 5. 数据面设计:透明隧道(L4 over WSS)

**关键决策:云端做 TCP 级透明隧道,而非 L7 反向代理。**
REST 请求、WebSocket 升级、终端字节流,全部作为不透明字节穿过,协议零适配。

### 5.1 三段连接

| 段 | 承载 | 说明 |
|----|------|------|
| daemon ↔ cloud | 1 条 WSS **控制+数据**长连接 | 上跑多路复用(streamId 分帧),类似 yamux;心跳 30s,断线指数退避重连 |
| mobile ↔ cloud | 每个会话 1 条 WSS(或复用) | 首帧 `claim{code}` 或 `connect{devId}` |
| daemon ↔ 本机 | 隧道流 ⟷ `127.0.0.1:<httpPort>` | daemon 收到 `accept` 后拨号本机端口,双向 pipe |

### 5.2 帧协议(草案)

```jsonc
// 控制帧(文本)
{"t":"hello",  "role":"daemon"|"client", "ver":1}
{"t":"reg",    "devId":"a3f9...", "sign":"<devSecret HMAC>"}        // daemon 注册
{"t":"code",   "code":"482913", "ttl":120}                          // daemon 上报配对码
{"t":"claim",  "code":"482913"}                                     // client 出示配对码
{"t":"open",   "streamId":7, "devId":"a3f9..."}                     // client→云→daemon 开流
{"t":"accept", "streamId":7}                                        // daemon 应答,流建立
{"t":"close",  "streamId":7, "why":"..."}

// 数据帧(二进制): [streamId(4B) | len(4B) | payload]  —— 原样转发,不解析
```

### 5.3 手机端接入方式

Flutter 侧实现 `RelayTransport`:

- `http` 层:自定义 `ConnectionClient`,把 HTTP 请求写进虚拟流、从流读响应;
- `WS` 层:现有 `WsClient` 的 socket 来源换为隧道流;
- 对上层 `RestClient`/`WsClient`/stores **完全透明**,业务代码零改动。

## 6. 安全设计

### 6.1 威胁模型

| 攻击者 | 能力 | 对策 |
|--------|------|------|
| 公网窃听 | 抓包手机/云之间流量 | 全程 TLS(WSS + Let's Encrypt) |
| 恶意扫码者 | 枚举 6 位配对码冒领 | 云端限速 + code 一次有效 + TTL 2min + daemon 失败锁定 |
| **云中继本身**(半可信) | 转发时可看到/篡改明文 | **端到端加密**(§6.3):云端只见密文 |
| 中间人(云作恶或劫持) | 冒充 daemon 与手机握手 | PAKE 配对(§6.4,M2 阶段) |

### 6.2 配对码防枚举

- 云端 `claim` 接口:每 IP 每分钟 ≤ 5 次,超限拉黑 10 分钟;
- code 一次性(领取即删)、TTL 120s、6 位数字;
- daemon 侧:连续 3 次 verify 失败 → 锁定 5 分钟(该措施同时利好现有局域网模式)。

### 6.3 端到端加密(E2E)

配对成功后,手机与 daemon 在隧道内协商会话密钥,之后隧道 payload 整体再包一层
AES-256-GCM(序列号防重放):

```
手机看到的:  https/wss 明文 ──E2E加密──► 密文 ──TLS──► 云 ──TLS──► 密文 ──解密──► daemon
```

- **云端不可见**:token、终端内容、任务数据全部是密文;服务器被攻破也拿不到数据;
- 密钥仅存两端(手机安全存储 + daemon 数据库),可随设备吊销轮换。

### 6.4 配对防中间人:为什么必须是 PAKE

⚠️ 安全推导(实现前必读):

- 配对码**必然经过云端**(云端要靠它路由),所以云端知道 code;
- 若只用「code 作为 PSK + HMAC 认证 ECDH 公钥」的简单方案,**知道 code 的云端可以双向
  分别握手冒充**,即 MITM —— 简单 PSK 认证挡不住"转发者冒充";
- 正解是 **PAKE 类协议(推荐 SPAKE2)**:双方各持 code,协商出共享密钥,且协议保证
  即使观测到全部交换报文(云端正好处在这个位置)也无法冒充任何一方、无法离线穷举 code。

**分期**:R1(见 §9)先上 TLS + 信任云端不作恶(与现网 frp 方案同级);
**R2 上 SPAKE2 + E2E 加密**,彻底消除对云端的信任依赖。文档在此明确记录该残余风险,
不允许 R2 缺席。

### 6.5 授权与吊销

- 设备 token 仍由 daemon 签发/存储(现有 `devices` 表),云端无权授信;
- Desktop 设置页已有设备管理,删除设备即吊销(对所有路径生效,含云隧道)。

## 7. 云服务 relay-server 设计

### 7.1 形态

| 项 | 决策 |
|----|------|
| 语言/框架 | Go(与 daemon 同栈,复用 chi + coder/websocket),单二进制 |
| 部署 | Docker Compose + Caddy(自动 TLS),与 `deploy/` 风格一致 |
| 状态 | 全内存:`code→devId`(TTL)、`devId→conn`、`streamId→pipe`;**无数据库** |
| 域名 | 如 `relay.shellsync.example.com`,证书 Let's Encrypt |

### 7.2 接口一览

| 端点 | 调用方 | 说明 |
|------|--------|------|
| `GET /health` | 运维 | 存活/版本 |
| `GET /metrics` | 运维 | 连接数、活跃流、带宽(可选 Prometheus 格式) |
| `WSS /ws` | daemon / mobile | 统一入口,首帧 `hello.role` 区分角色(§5.2 帧协议) |

### 7.3 容量与成本估算

- 终端交互流量为 KB 级/秒,单台 **2C4G、按流量计费** 的 VPS 保守支撑 **数百并发会话**;
- 成本:**¥30~60/月**(VPS)+ ~¥50/年(域名);
- 扩容路径:按 `devId` 哈希分片多台(daemon 重连即被调度),`cloud` 字段可下发多地址;
  单机起步完全够,不需要一开始就设计分布式。

### 7.4 运维基线

- 进程崩溃自动重启(compose `restart: unless-stopped`);
- daemon 侧断线重连(指数退避),云端重启对用户表现为秒级闪断;
- 隐私红线:不记录流量内容;日志仅含连接元数据(IP、devId 哈希、时间、字节数)。

## 9. 实施里程碑

| 阶段 | 内容 | 验收标准 |
|------|------|----------|
| **R1 云中继 MVP** | relay-server + daemon 出站注册 + 手机隧道;TLS + token + 云端限速 | 手机用流量扫码配对成功,终端可交互;同网仍走局域网 |
| **R2 安全加固** | SPAKE2 配对、端到端加密、daemon 失败锁定 | 抓包云端入口全部密文;伪造 code 无法完成握手 |
| **R3 体验优化** | P2P 打洞(UDP/ICE)优先、中继兜底;连接路径可视化 | 同网/NAT 友好场景 P2P 命中,延迟明显下降 |
| **R4 规模化** | 多节点分片、监控告警、用量统计 | 并发用户增长时水平扩容;可观测 |

## 10. 备选方案对比(决策依据)

| 方案 | 一键式 | 跨网 | 成本 | 结论 |
|------|:--:|:--:|------|------|
| **官方云中继(本方案)** | ✅ | ✅ | 开发者一台 VPS | **采用** |
| 用户自建 frp(`deploy/`) | ❌ 要装 3 样东西 | ✅ | 用户自己承担 | 保留为「自托管模式」 |
| Tailscale/ZeroTier | ❌ 手机装 VPN + 第三方账号 | ✅ | 免费/订阅 | ❌ 依赖第三方,体验割裂 |
| 纯 P2P 打洞 | ✅ | ⚠️ CGNAT 成功率不稳 | 一台信令服务器 | ❌ 必须有中继兜底,即回到本方案 |

## 11. 与现有架构的兼容性

- 桌面端、daemon 的局域网工作方式**原样保留**:拔掉云,系统退化为现状;
- `deploy/` frp 方案与云中继共用 daemon 的 relay 模块 —— `cloudURL` 指向自建的
  relay-server 即"私有云",一套代码两种部署;
- 二维码 v2 向后兼容 v1,新旧版本 App/daemon 可混用(老 App 扫新码走局域网)。

## 12. 遗留问题(待评审)

1. 多台电脑共用一部手机:当前手机只存一组凭证,需扩展为设备列表切换(devId 已天然支持);
2. 云端是否注册域名备案(国内 VPS 需备案,海外 VPS延迟稍高,二选一);
3. R2 的 SPAKE2 选型:Go 侧有成熟实现,Flutter/Dart 侧需要评估库或自行移植;
4. 免费/收费边界:个人免费、流量限额策略(R4 时再定)。
